## Recommendation

**Decision:** Port the platform to direct Rust bindings for Apple frameworks, with AppKit owning the macOS shell and the existing Vexel UI remaining custom drawn. Keep AppKit types behind `platform/` interfaces. This fits the owner’s macOS 13+, custom UI, and no shipped first-party C/Objective-C requirements.

**Facts, checked 14 Oct 2026:** The objc2 project provides Rust bindings to Apple frameworks. Its published AppKit, Core Graphics, Core Text, and Metal crates are each at **0.3.2**, released **4 Oct 2025**. They use `Zlib OR Apache-2.0 OR MIT`; objc2’s core crate uses MIT. The project notes that its bindings derive from Apple SDKs and flags Xcode license terms as an area of uncertainty, so record that caveat for dependency review. The Metal crate’s published lockfile pairs 0.3.2 with `objc2 0.6.2`. [objc2 project and license](https://github.com/madsmtm/objc2), [AppKit 0.3.2](https://docs.rs/crate/objc2-app-kit/0.3.2), [Core Graphics 0.3.2](https://docs.rs/crate/objc2-core-graphics/0.3.2), [Core Text 0.3.2](https://docs.rs/crate/objc2-core-text/0.3.2), [Metal 0.3.2 and package lockfile](https://docs.rs/crate/objc2-metal/0.3.2).

**Inference / dependency proposal:** Start with `objc2`, `objc2-foundation`, `objc2-app-kit`, `objc2-core-graphics`, `objc2-core-text`, `objc2-metal`, and QuartzCore bindings for `CAMetalLayer`; enable only needed API features. Add `block2` for Objective-C completion blocks where required. Add `dispatch2` only if the design needs explicit GCD dispatch. Pin the compatible published versions and resolved transitive graph in a reviewed ADR/lockfile; the 0.6.2 pairing is evidence, not a claim that it is the newest objc2 release. Apple frameworks are OS dependencies, not vendored UI code. Review each API’s macOS availability against the 13.0 deployment target.

## UI choice

**Native bindings vs egui:** egui is MIT OR Apache-2.0, immediate-mode, custom paintable, and has optional AccessKit accessibility. It can produce a custom appearance, so it is not inherently incompatible with the visual lock. However, adopting it would replace Vexel’s retained widget/state/layout and pixel-painter modules, while AppKit integration would still be needed for shell, dialogs, menus, clipboard, and Metal. **Inference:** Direct bindings are the narrower migration path and better preserve the existing custom UI architecture. [egui repository, current manifest and license](https://github.com/emilk/egui).

## Scope and seams

Cover `src/platform/macos/` (window/events, menus, dialogs/files, clipboard, accessibility, Metal, text/localization, recovery and task queue); `src/ui/` (core, widgets, drawing, icons and viewer controls); and `src/app/` viewer runtime, events, rendering, chrome, editor, timeline and accessibility modules. The local READMEs and platform headers document current behavior and contracts.

Retain the platform seam as owned Rust types: opaque window/resource handles, bounded UTF-8 and byte buffers, explicit event/action enums, and owned event payloads. Keep application/editor models independent of AppKit classes. Match existing semantics for point-space input versus backing-pixel surfaces, scale-change events, key/modifier translation, file-open/drop paths, asynchronous open/save completion, command-state menus, native dialogs, bounded SVG/PNG clipboard formats, Core Text measurement/drawing, and VoiceOver names, values, actions, frames and change notifications. Apple documents that AppKit UI work belongs on the main thread; keep view/window/menu/dialog/clipboard/accessibility operations there and move parsing/raster/recovery work off-thread. [AppKit threading guidance](https://developer.apple.com/documentation/technologyoverviews/uikit-appkit), [NSApplication event loop](https://developer.apple.com/documentation/appkit/nsapplication), [NSPasteboard](https://developer.apple.com/documentation/appkit/nspasteboard), [NSAccessibilityProtocol](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol).

## Ownership, sequence, and risks

Keep `unsafe` inside a small platform FFI layer: document each pointer’s lifetime, retain/autorelease transition, callback/block capture, thread affinity and teardown order. Prefer objc2 retained handles and Rust-owned snapshots. Never let a callback outlive its window/app context; cancel or invalidate callbacks before releasing handles. `objc2` exposes retained Objective-C objects, but safe wrappers do not remove the need to uphold API invariants. [objc2 `Retained`](https://docs.rs/objc2/latest/objc2/rc/struct.Retained.html).

**Ready work-order sequence:** (1) freeze platform Rust types, FFI/thread/ownership rules and deployment target; (2) port AppKit startup, window, input/event queue and teardown; (3) dialogs, file open/drop, menus, clipboard and command routing; (4) Core Text, appearance and accessibility parity; (5) Metal device/layer/pipeline/presentation and bounded verification; (6) Rust UI primitives and viewer/chrome/editor integration; (7) native parity and accessibility acceptance, then retire C/Objective-C implementations only after verified parity.

**Risks/unknowns:** Generated binding feature coverage and exact API availability need a symbol-by-symbol macOS 13 audit. Screen-coordinate conversions, display changes, Objective-C callback lifetimes, responder/key-equivalent behavior, and VoiceOver interaction require interactive macOS verification. This is a migration plan, not evidence of performance or binary-size gains; neither is guaranteed without measurement.
