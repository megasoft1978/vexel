# Deeper engineering research gaps and recommended defaults

Numbers marked **estimate** are design targets, not published benchmark claims. Published benchmark data is version/hardware specific. The linked round-two sources remain useful; this pass adds direct project/docs where possible.

## B1. Custom C UI

Use a retained **semantic widget tree** (stable widget IDs, parent/child, bounds, role/name/value/state/actions) and a per-frame immediate **paint command stream**. This gives stable focus/accessibility/undo/event identity without requiring retained GPU objects. Default layout is flexbox-like constraints with a single top-down measure/arrange pass plus bounded second pass for intrinsic text. Clay is a useful small C reference for declarative layout, but not the whole UI. Dear ImGui docking and Nuklear show immediate widget patterns; they do not solve accessibility/IME for this product. RAD Debugger, GPUI, Flutter and Makepad are architecture references only. [Clay](https://github.com/nicbarker/clay) [Dear ImGui docking](https://github.com/ocornut/imgui/wiki/Docking) [Nuklear](https://github.com/Immediate-Mode-UI/Nuklear) [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview) [GPUI](https://github.com/zed-industries/zed/tree/main/crates/gpui)

Minimum widget set: app/menu bar and commands; dockable split panes; tabs; layer/object virtual tree; property inspector; color picker; numeric fields with keyboard entry and drag scrubbing; slider; checkbox/radio/dropdown; context menu; tooltip; searchable command palette; text field with selection, clipboard and IME; scroll views with trackpad momentum; dialogs delegated to OS; canvas and selection handles. Virtual lists use visible rows + overscan and stable IDs, so one million XML/layer rows allocate O(viewport rows), not O(N) widget objects. Docking should start as fixed panes with draggable splitters, defer arbitrary tear-off docking.

Architecture details: central command registry (ID, label, shortcut, enabled predicate, execute callback, undo policy); keyboard routing: text input → focused widget → modal → focused panel → document/tool commands → app; pointer capture per pointer ID; gesture arena resolves drag vs click vs pan; event positions are logical points, convert once to physical pixels. Property edits open one undo transaction at pointer-down/focus, update preview on motion, commit once on release/Enter, cancel on Escape. DnD has typed MIME payloads and hover/drop targets. Tooltips delayed (~450 ms proposed), animations use monotonic clock and easing; respect reduced-motion preference. Localization: UTF-8, message catalog, plural rules, no concatenated sentences; RTL requires mirrored layout and bidi text, so do not assume just translating labels.

High DPI: preserve logical units, query per-window/per-monitor scale, rebuild raster cache on scale change; test fractional scales 1.25/1.5/1.75. Mac frame pacing via CVDisplayLink or CAMetalLayer drawable timing; event-driven invalidation plus 60/120 Hz cap; no busy loop. Redraw dirty widget/canvas tiles only; panels redraw when state/damage changes, canvas invalidates impacted tiles. Accessibility tree must map to native NSAccessibility, UI Automation, AT-SPI via thin shims; macOS core controls are MVP, other OS adapters by M11/12. CoreText on macOS is permitted system service; Linux shaping recommendation HarfBuzz+FreeType vendored or system dynamic libs remains ADR, Windows DirectWrite.

## B2. CPU rasterizer

Recommendation: **do not start with a complete custom scan converter**. M4 spike PlutoVG (MIT, C) vs a small in-house scalar tile fill; use the library only behind `raster_backend.h`, pin commit/hash, license audit, corpus test. PlutoVG is about 19,004 ANSI C SLOC in Debian's 1.3.3 source listing, so not a tiny header. Its feature coverage and benchmark fit must be checked. Blend2D is C++ and its own benchmark compares 8–256px primitive workloads; it is not an independent SVG end-to-end result. No apples-to-apples current Apple Silicon comparison among Blend2D, Skia, Cairo, AGG, resvg/tiny-skia, ThorVG and Vello was verified; publish none as universal. [PlutoVG](https://github.com/sammycage/plutovg) [Debian SLOC](https://sources.debian.org/src/plutovg/1.3.3-1/) [Blend2D methodology](https://blend2d.com/performance.html) [Wikimedia SVG benchmark (2021 data)](https://www.mediawiki.org/wiki/SVG_benchmarks)

Pipeline: parse paths into immutable segments; transform to device; conservative bounds; flatten curves with device-space flatness target 0.25 px (quality knob 0.1–0.5); bin display items to 32×32 or 64×64 pixel tiles; each tile job consumes immutable commands in painter order and writes a private premultiplied RGBA buffer; publish tile generation only if document/view generation matches. For fills, use scanline edge crossings or analytic area coverage (A-buffer/coverage accumulation) with even-odd/nonzero winding. Compare PlutoVG's method first. Sparse bins store ranges for occupied tiles; large shapes use a global/oversized list to avoid million-bin duplication. Culling uses transformed bboxes, clips and viewport. Cache key includes object/style/transform bucket, zoom scale, color-space, device scale; tile LRU budget (proposed 256 MiB default, adjustable), cancel invalidated work.

Strokes are the highest geometry risk: stroke expansion needs joins/caps/dashes, cubic offset approximation, cusp/self-intersection handling and miter limit. Start with path stroking from vendored engine; add scalar fallback and heavy edge-case tests. Tiller–Hanson-style polygon-offset methods are approximations; not a proof of standards fidelity. Skia exposes butt/round/square caps and miter/round/bevel joins; Vello's GPU-friendly stroke expansion paper is useful algorithm research, not evidence it is ready as a C CPU solution. [Skia stroke API](https://github.com/google/skia/blob/main/include/core/SkPaint.h) [GPU-friendly stroke expansion paper](https://arxiv.org/abs/2405.00127)

Gradients: evaluate in correct objectBoundingBox/userSpace coordinates, spread pad/repeat/reflect; cache stop ramps. Clips/masks require bounded offscreen tiles and recursion limits; filters deferred/unsupported diagnostic in first pass. Blend compositing uses premultiplied alpha. Choose internal linear-light float/16-bit for filter/composite correctness, but present sRGB BGRA8/RGBA8 and measure; clarify CSS color interpolation semantics per effect. SIMD: scalar reference, NEON implementation for pixel blend/gradient spans first; wrapper via compiler intrinsics with runtime feature detection; never put vector types in public API. Worker pool has fixed threads, bounded queues, no per-pixel allocations.

Metal presentation: simplest M1 path is a CPU tile atlas copied to a `MTLTexture` (shared storage on unified Apple Silicon where supported, otherwise managed/private upload path), then a full-screen quad via CAMetalLayer. Do not assume direct CPU pointer access to drawable texture. Benchmark upload bytes/frame and avoid copying clean tiles; IOSurface sharing is optional later. Metal docs [resource storage modes](https://developer.apple.com/documentation/metal/choosing-a-resource-storage-mode-for-apple-gpu-resources).

## B3. Large-file architecture and safety

Keep a read-only source mapping alive for the document; never mutate mapped bytes. Parse into source-span records and lazily decode attributes/path data. XML lexical scan must handle quotes, comments, CDATA, PI, DOCTYPE policy, UTF-8 validation; delimiter SIMD is an optimization after scalar correctness. One pass creates token/element index and lightweight root/namespace/style refs; second pass resolves IDs, `use`, CSS and geometry. Alternative two-pass memory savings vs extra I/O should be benchmarked. `mmap` avoids initial copy but page faults and file replacement behavior vary; fallback buffered read.

Proposed compact record (estimate): 32 bytes/node: parent `u32`, first-child/next-sibling `u32` each, source start/end `u64`, kind/flags `u16` each, small attr/style indexes `u32`; IDs, strings, decoded attributes live in separate vectors/hash table. At 1M nodes: 32 MB records; add indexes/IDs 16–40 MB, decoded visible geometry 40–200 MB, caches separately bounded. At 10M nodes: 320 MB records alone, so cap editable node count or use 24-byte records/segmented disk-backed index; map input bytes remain virtual but resident pages still count RSS. These are estimate layouts. Do not promise a 1 GB file fits a 256 MB process.

Worked estimate at 32-byte element record:

| Elements | Base records | Estimate with indices + hot decoded geometry (4–8× record bytes) |
|---:|---:|---:|
| 1M | 32 MB | 128–256 MB |
| 10M | 320 MB | 1.28–2.56 GB |

For 10M, use compressed/segmented index or reject with a clear limit; prove on measured workloads. Progressive first paint requires only root viewport, basic styles, and visible object geometry; keep parsing in background with cancellation and stale generation IDs. Tile LOD may omit individual geometry below 0.5 device-pixel contribution only if conservative area/coverage bounds preserve appearance; do not drop semantic objects from edit tree. Build STR-packed R-tree after first paint in background; estimate: 10M entries at 32–48 bytes ≈320–480 MB plus node pages; build-time is unknown and must be measured, likely unacceptable synchronous. Start with incremental loose quadtree/BVH or chunked spatial cells; benchmark 100k, 1M, 10M.

Embedded `data:` images: retain source span, scan declared media type and encoded size, do not decode until visible/on demand; limit encoded bytes, decoded dimensions/pixels, total decoded image cache. External references disabled by default. `<use>` graph resolution must detect cycles and bound depth (e.g. 64) and expanded instance count (e.g. 5M) with warning. XML security: no external entities/network; reject or disable DTD; entity expansion count/bytes, nesting depth (e.g. 256), attributes/node/path command count, numeric magnitude, CSS recursion and filter surface pixels all capped. Values proposed for tuning, not standards maxima. Fuzz parse, stylesheet, path, transform and serialization; preserve original when unsupported.

Comparable systems: simdjson demonstrates staged structural indexing for JSON, but XML grammar/quotes mean adapting is not direct. Mapbox/Tippecanoe's tile/LOD generalization offers useful spatial tiling ideas but sacrifices feature detail; QGIS/PostGIS use spatial indexes for query/render, not editable SVG source; resvg is an oracle but builds scene. No verified public 1 GB SVG memory benchmark or Chromium hard SVG element limit found. [simdjson](https://github.com/simdjson/simdjson) [Tippecanoe](https://github.com/felt/tippecanoe) [QGIS rendering](https://docs.qgis.org/latest/en/docs/pyqgis_developer_cookbook/canvas.html) [resvg tests](https://github.com/linebender/resvg/tree/main/tests)

## B4. Editing model

Source spans stay authoritative for untouched regions. Parse semantic records lazily; edits create an overlay/op log (attribute set, node insert/delete, path replacement), never patch mapped bytes. On save, emit source slices and edits in order; reserialize only changed element ranges and ancestors needed to maintain well-formedness. Reparse saved output in test. Preserve namespace declarations, `inkscape:`/`sodipodi:` attributes, unknown elements and comments. Keep original attribute/style text until user changes it; no global normalization. IDs are indexed, collisions repaired only for newly created IDs; existing duplicate IDs produce diagnostics. CSS `<style>` must be source-preserved; MVP supports subset cascade and edits explicit presentation attributes or scoped declarations without flattening unrelated CSS.

Document IDs use generation handles `(slot,generation)` rather than retained pointers. Geometry path data is decoded on demand into commands; node editor supports select/add/delete, drag node/handle, cusp/smooth/symmetric conversion, close/open path, snap to grid/guides/nodes. Transform operations preserve `transform` attribute by default; “bake transform” explicit and tested for stroke-width/vector-effect and nested groups. Hit testing uses spatial index broad phase + exact fill/stroke query; selection overlay separate from document renderer. Boolean ops are OUT for MVP; if later needed, vendor Clipper2 (Boost license) behind geometry API and document integer quantization/error policy; robust cubic booleans are a large scope.

Undo records semantic inverse operations plus source snapshots for changed spans; transactions merge pointer drags into one action. Save must be atomic temp+rename with backup/recovery journal. MVP: select/move/scale/rotate, node editing, basic fill/stroke/opacity/linear/radial gradients, layers visibility/lock/order, undo/redo. No path effects, mesh gradients, filters editing, extensions or arbitrary XML editing beyond read-only inspection initially.

## B5. Animation later

SMIL animation elements and CSS animations can coexist in SVG; modern browser support remains engine-dependent and should be verified against current compatibility tables during M13. Chrome's Blink restored SVG SMIL animation support in 2016; WebKit and Gecko document their supported SVG/CSS animation behavior. Mark SMIL as **not deprecated from the SVG format**; it was once slated for removal in Chromium then retained. Support in SVG animation timeline is not equivalent to full browser parity. Sources: [SVG Animations spec](https://www.w3.org/TR/SVG/animate.html), [Chrome SMIL status](https://developer.chrome.com/blog/smil), [MDN SVG animation](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/animate), [Can I Use SMIL](https://caniuse.com/svg-smil).

Use SMIL as interoperable output where practical; CSS keyframes for CSS properties; private namespace metadata may store editor-only easing/track UX only if static SVG remains valid. Round-trip timing tests in Chromium, Firefox, Safari; static fallback frame; deterministic timeline model (rational time ticks, property tracks, keyframes, begin/duration/repeat/fill). Lottie export optional and lossy; never source of truth. Do not put animation in MVP.

## B6. Native shim, OS services, packaging

Thin does not mean no dependencies: each OS requires its event/window/compositor APIs and a11y/input/text services. **macOS first:** Cocoa/NSApplication/NSWindow, CAMetalLayer/Metal, CoreText, NSPasteboard, NSOpenPanel/NSSavePanel, NSAccessibility, NSTextInputClient/IME, menus, CVDisplayLink or drawable pacing. Objective-C/Objective-C++ shim is acceptable around C17 core. **Windows:** Win32 window/input, DirectWrite/Direct2D only for text shaping/system service, TSF IME, clipboard/OLE DnD, common dialogs, UI Automation; present through D3D11 + DXGI swap chain, optionally DirectComposition for overlays. **Linux:** choose GTK-free native X11 and Wayland paths or a C platform layer; Wayland requires `libwayland-client`, xdg-shell protocol, `xkbcommon`, text-input-v3 where available; decorations via xdg-decoration/libdecor or client-side frame; file portal via D-Bus xdg-desktop-portal. Don't implement Wayland wire protocol directly. X11 is legacy support. Relevant specs: [Wayland xdg-shell](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/stable/xdg-shell/xdg-shell.xml), [text-input-v3](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/unstable/text-input/text-input-unstable-v3.xml), [libdecor](https://gitlab.freedesktop.org/libdecor/libdecor), [xkbcommon](https://xkbcommon.org/), [portals](https://flatpak.github.io/xdg-desktop-portal/).

Sokol app/GLFW/SDL3 can reduce backend work but are window/input frameworks (not widget UIs) and may violate “thin shims”; exact backend LOC changes by version/config, so avoid stale LOC claims. Pin and count checked-out source at ADR review. Expected distribution is **estimate**: stripped single-arch core executable 2–8 MB plus platform frameworks/assets; macOS signed `.app` 8–25 MB (universal 12–35 MB); Windows portable 6–20 MB; Linux AppImage/Flatpak 15–60 MB due runtime/deps. These ranges are provisional and can be wrong by 2×; measure M1/M14. macOS Developer ID signing/notarization/stapling required for frictionless outside-store distribution [Apple](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution). Windows use signed portable ZIP/MSIX, Linux Flatpak/AppImage or distro packages; static-musl may not integrate well with desktop services and is not default.

## B7. C17 safety

Use opaque public handles, checked slices `{const uint8_t *ptr; size_t len;}`, explicit mutable slices, checked add/multiply/align helpers before allocation, no VLAs, no `strcpy/strcat/sprintf`, no unbounded recursion, no implicit signed/unsigned conversions, no public ownership ambiguity. Arenas: document-lifetime source/index arena; per-parse scratch; per-frame UI arena; tile/job scratch; reset only on owner thread. Handles include generation; workers receive immutable snapshots/refcounted backing mapping and cancellation token, never raw pointers into mutable vectors. Allocation failure returns status and leaves old document intact.

Compiler: `-std=c17 -Wall -Wextra -Wpedantic -Wconversion -Wshadow -Wstrict-prototypes -Werror` with reviewed suppressions; `-fstack-protector-strong`, fortify where applicable; ASan+UBSan on every PR, MSan where supported, TSan concurrency suite nightly; fuzz targets libFuzzer for XML, path data, CSS, transform, serializers; static `clang --analyze`, CodeQL or equivalent; dependency/license audit. Apple Clang `-fbounds-safety` is experimental/toolchain-dependent, evaluate as optional; not a substitute for bounds-correct APIs. CHERI and ARM MTE are useful future defense-in-depth, not cross-platform baseline. C's realistic Rust alternative: Rust would reduce classes of lifetime/data-race mistakes and offers SVG ecosystems, but is explicitly out under the owner-locked language choice; disciplined C still cannot provide equivalent compiler-enforced memory safety. [CERT C](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/front-matter/introduction/) [Clang sanitizers](https://clang.llvm.org/docs/AddressSanitizer.html) [Clang static analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html)

## B8. Test and benchmark system

Corpora: W3C SVG 1.1 suite; resvg tests (~1.6k in current corpus claim from prior round; pin exact commit/count), SVG2 tests; WPT SVG; Inkscape `testfiles`; privately donated target-user docs with consent and redaction; generated 1/10/100/500 MB and 1 GB files covering nodes, object count, raster payload and filters separately. Manifest includes source/license/hash, expected support status, expected output and feature tags. [W3C suite](https://www.w3.org/Graphics/SVG/Test/Overview.html) [WPT SVG](https://github.com/web-platform-tests/wpt/tree/master/svg) [Inkscape corpus](https://gitlab.com/inkscape/inkscape/-/tree/master/testfiles) [resvg tests](https://github.com/linebender/resvg/tree/main/tests)

Pixel comparison: deterministic CPU golden exact hash where supported; cross-renderer expected differences use linearized pixel diff with 99.9% pixels within ΔE00≤2 and edge masks threshold ≤1 px as proposed; classify known deviations. For GPU exact image hashes are too brittle across drivers; use per-platform golden/tolerant metrics plus structural feature assertions. Round-trip: byte equality unchanged source where feasible; otherwise semantic canonical XML comparison plus unknown subtree byte/source-span retention tests. UI: headless command paint raster + semantic accessibility tree snapshots + scripted normalized pointer/key/IME input; test focus order, screen-reader names, undo grouping, virtual list million rows bounded allocations. Performance CI stores machine/OS/build/corpus hashes and median + p95, compare same-runner baselines; flag >10% regression in stable benchmarks, do not hard-fail noisy shared runners. Use dedicated Apple Silicon Mac mini runner (self-hosted) for meaningful arm64; hosted macOS availability/cost depends provider/plan and is unknown until procurement. Keep latency, peak RSS, allocated bytes, CPU energy/frame, file size, binary/app package size, and first-paint checkpoints separate.
