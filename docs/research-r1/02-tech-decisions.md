# Technical decisions (Q3–Q6)

**Decision:** benchmark two complete vertical slices before locking the stack. Recommendation for the stated priorities is C++20 + C ABI as pragmatic default, or Rust core + C ABI if the team has Rust strength. Do not select C because “C is fast.” If C is mandatory, C17 is the conservative baseline; evaluate C23 compiler support across macOS Clang, MSVC, and GCC before adopting it. **C23 production portability in late 2026: verify exact toolchain matrix; unknown here.**

## Language decision

| Choice | Strengths for this product | Costs / risks | Decision |
|---|---|---|---|
| **C11/C17/C23** | Simple ABI, portable, predictable control over layout/allocations; easy to embed native OS and C libraries. | Memory/lifetime bugs are not prevented by type system; no built-in generics/RAII; object graph, undo, asynchronous work and error paths become convention-heavy. C23 gives no SVG ecosystem advantage; GCC lists C23 support, while Clang’s C23 implementation status page remains under investigation (MSVC support for the selected feature set is unknown). [GCC](https://gcc.gnu.org/projects/c-status.html) · [Clang](https://clang.llvm.org/c_status.html) CERT C rules are necessary but not sufficient for safety. [CERT C guidance](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/front-matter/introduction/) | Use only if owner’s C requirement is firm. Prefer C17 initially, opaque handles, limited public structs, arenas for parse snapshots, explicit ownership annotations and static analysis. |
| **Rust** | Strong memory safety for untrusted files and concurrency; resvg/tiny-skia ecosystem; C ABI available. [resvg](https://github.com/linebender/resvg) | UI/tooling ecosystem less uniform for desktop creative apps; unsafe FFI still requires audit; dependencies can affect bundle and compile times. | Best safety-led engine choice; GTK integration or Rust core with C ABI. |
| **C++20** | Mature native graphics/UI ecosystem; Qt/Skia/2geom/Clipper integrations; RAII, templates, established desktop-app patterns; C ABI boundary feasible. | Complex language and build system; ABI and lifetime bugs still possible; C++ does not guarantee readable code. | Most pragmatic all-platform desktop choice with strict subset/style and C ABI. |
| **Zig** | C interop, explicit allocators, cross compilation. | SVG/editor ecosystem and mature GUI/tooling smaller; project-level risk is high for a parity application. | Not selected for core. Revisit if ecosystem matures and team has expertise. |
| **Go** | Good tooling, concurrency, readable syntax. | Desktop graphics/UI and SVG editor ecosystem less suited; GC and runtime complicate tight memory budgets / object graph control. | Not selected. |

**If C is fixed:** define `status_t` return values and `error_t*` out parameters; no process-global mutable state; allocator passed into constructors or document context; one owner per object; borrowed pointers documented with lifetime; opaque structs at module boundaries; `const` inputs; overflow-checked allocation arithmetic; no setjmp error unwinding; no callbacks into freed objects; lock ordering documented. Compile debug and release with `-Wall -Wextra -Wpedantic -Wconversion -Wshadow` where supported, plus ASan/UBSan/TSan, clang static analyzer, clang-tidy where useful, cppcheck, and fuzzing. C cannot satisfy “safe” through style alone.

### Minimal stack proposal

- **C/C++ boundary:** C17 application/core with optional C++ renderer via opaque C ABI, or C++20 throughout; avoid mixing allocator ownership across boundary.
- **Parse:** libxml2 if editable DOM/XPath is required, securely configured; otherwise Expat tokenizer plus application-owned loss-preserving XML structure. `mmap` input only as a byte source, not as mutable DOM.
- **Render M1:** resvg CLI/library as oracle/reference; prototype ThorVG and Blend2D. Select after matching SVG fixtures and performance. No library named above alone covers Inkscape’s entire document semantics.
- **Text:** HarfBuzz + FreeType initially; optional CoreText comparison on Mac.
- **Geometry:** independent path model + tested boolean implementation; consider Clipper2 only for polygon operations; no claim of exact cubic boolean parity from polygon clipping.
- **Color/images:** LittleCMS2 plus libpng/libjpeg-turbo/WebP only if required; cap decoded image dimensions and memory.
- **PDF:** adapter to CapyPDF or Cairo after feature fidelity spike; defer PDFium.
- **Animation:** first author SVG SMIL subset; optionally Lottie export later via established runtime.

## UI toolkit decision

| Option | Good at | Limits for this editor | Verdict |
|---|---|---|---|
| Native AppKit / Win32 / GTK per OS | Native accessibility, menus, IME, platform feel; AppKit standard controls have built-in accessibility and GTK4 maps accessibility to AT-SPI/NSAccessibility/Windows APIs. [AppKit](https://developer.apple.com/documentation/appkit/accessibility-for-appkit) · [GTK4](https://docs.gtk.org/gtk4/section-accessibility.html) | Three UI implementations and behavior drift; macOS-first still leaves Windows/Linux costly | Consider native shell over a shared canvas only if native UX is strategic. |
| **Qt 6 Widgets/Quick** | Mature cross-platform desktop, accessibility infrastructure, IME, model/view, HiDPI, native OpenGL/Metal-adjacent integration | Larger dependency/deployment surface; LGPL/GPL/commercial obligations and GPL-only Qt modules. [licensing](https://doc.qt.io/qt-6/licensing.html) | **Recommended pragmatic default** for designer-facing retained UI; package-size spike before adoption. Do not use GPL-only modules if product license incompatible. |
| **GTK 4** | Native Linux/GNOME, C API, accessibility and scalable list models; GTK4 documents Windows and macOS backends and accessibility mappings. [GTK4 docs](https://docs.gtk.org/gtk4/) · [accessibility](https://docs.gtk.org/gtk4/section-accessibility.html) | Windows/macOS polish and packaging remain nontrivial; platform integration needs validation | Strong choice if Linux/open-source ecosystem is priority; 1.5 work shows ongoing port churn. |
| Dear ImGui | Fast tooling, docking, testing, custom canvas; MIT; draw lists easy to render. [repo](https://github.com/ocornut/imgui) | Immediate-mode control tree needs accessibility, IME, screen-reader and desktop semantics work; poor default for a complex consumer editor | Use for internal tools/prototypes, not full app UI. |
| Nuklear | ANSI C, tiny, MIT/public domain, no window/render backend dependency. [repo](https://github.com/Immediate-Mode-UI/Nuklear) | Same accessibility/input/toolkit gaps; ~18k LOC claim is repo-reported, not whole application cost | Not full application UI. |
| SDL3 + custom UI / Raylib | Excellent event/window/canvas and GPU abstraction; SDL GPU API uses Metal/D3D/Vulkan backends. [SDL GPU](https://wiki.libsdl.org/SDL3/CategoryGPU) | Must build menus, text widgets, accessibility, IME, docking, file dialogs and UX infrastructure | Good rendering host, poor solo-team UI choice. |
| Flutter / Skia | Cross-platform custom UI; official docs list native Windows/macOS/Linux desktop support and accessibility APIs. [desktop](https://docs.flutter.dev/platform-integration/desktop) · [accessibility](https://docs.flutter.dev/ui/accessibility) | Runtime/framework bundle and memory; native editing conventions; SVG/document fidelity disconnected from Skia | Viable only if richer UI/runtime outweighs size target. |
| WebView / Electron | Web UI skills, CSS UI, fast iteration | Browser engine footprint; native file/IME integration and huge-document canvas tuning; increases size/RSS | Avoid for “minimal bundle/memory”; use embedded web docs only. |
| Clay / microui | Small immediate-mode/procedural UI prototypes | Immature application-level accessibility/widget ecosystem | Do not anchor product on them. |

**Mac-first requirement:** M0 must measure universal Mach-O binary, signed `.app` compressed DMG, cold startup, resident memory and Metal/native display behavior. UI toolkit feature claims do not predict package size. A split shell is possible: AppKit window/accessibility + shared C/C++ canvas and model; it increases platform code but gives strongest Mac feel.

## Large-file strategy

| Technique | Use and guardrail |
|---|---|
| Memory-mapped source bytes | Fast file reads and stable source slices; not a substitute for bounded parser allocations. Handle files larger than address space, truncation, replacement and Windows mapping semantics. |
| Streaming parse + lazy scene | Parse structure incrementally; retain unknown XML and byte spans. Materialize computed style, geometry, raster cache only when visible or needed by operations. Parsing must still validate the whole document before save. |
| Arena allocation / interning | Per-load arena for immutable parse data and interned namespace/name/style tokens. On edit, use document-owned pools and generation IDs; avoid dangling cross-arena pointers. |
| SoA for hot indexes | Use compact arrays for bounding boxes, transforms, visibility, selection bits and spatial bounds; keep rich per-element records for editing and unknown XML. Avoid duplicating all data in multiple trees. |
| Spatial index | R-tree for document-space bounds; update only affected objects on edit; query visible region, hit test, snapping candidates. Index does not replace dependency graph for `use`, filters, clip/mask and CSS. |
| Tile cache / dirty rectangles | Invalidate only changed bounds plus filter expansion; prioritize visible canvas tiles; cancel obsolete renders by document generation. Parallelize immutable display lists. |
| GPU and LOD | GPU helps panning, zooming, compositing; path tessellation and filters can bottleneck or cause cache expansion. Use simplified geometry at low zoom only for preview; precise export and node editing must use original geometry. |
| Background workers | Parse, thumbnail, trace, boolean operations and exports off UI thread; immutable snapshots or command queues; never call UI toolkit from worker. |
| Undo deltas / persistent data | Store compact operations and shared immutable subtrees; cap history by measured memory. Preserve enough source state for exact undo and round-trip. |
| Huge filters/images | Clip filter regions to viewport where semantics permit; tile and bound surfaces; decode images lazily; enforce dimensions/pixel-count limits before allocating. |

**M0 benchmark corpus (proposed, not published data):** 1k/10k/100k-object SVGs, 1M-node path, clone-heavy map, filter-heavy artwork, text-heavy multilingual page, many embedded PNGs, and a deliberately adversarial deeply nested document. Record load time, first paint, pan/zoom p95, edit latency, peak RSS, CPU time, cache bytes, export match. An `N MB` source file is not a useful standalone workload definition.

**Evidence boundary:** Inkscape's 1.3 notes document asynchronous multi-threaded tile rendering and 2–4× zoom/pan/transform gains on multicore; they explicitly state OpenGL mode does not render SVG content on the GPU. [release notes](https://wiki.inkscape.org/wiki/Release_notes/1.3) Its architecture has separate XML/object trees, so a new editor should avoid maintaining redundant full semantic copies unless profiling proves needed. [architecture](https://wiki.inkscape.org/wiki/Architectural_overview)
