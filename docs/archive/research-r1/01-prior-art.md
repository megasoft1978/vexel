## Inkscape itself: roadmap and animation

- **1.4** shipped on GTK 3, while substantial refactoring prepared the GTK 4 branch. Release notes explicitly called out a Windows performance regression risk during the GTK 4 transition. [1.4 notes](https://wiki.inkscape.org/wiki/index.php/Release_notes/1.4) · [GTK migration discussion](https://lists.inkscape.org/hyperkitty/list/inkscape-devel%40lists.inkscape.org/thread/6G3P3RZUJYTRKM7UNI4QDOWCNLY5EII4/)
- **1.5** remained the development branch as of the release index. Draft notes list GTK 4, a color management redesign, and CapyPDF PDF export. June 2026 developer minutes mention a new renderer under active development and ongoing text-performance work; this is not yet evidence of a released, stable renderer. [release index](https://wiki.inkscape.org/wiki/Release_notes) · [1.5 notes](https://wiki.inkscape.org/wiki/Release_notes/1.5) · [June minutes](https://lists.inkscape.org/hyperkitty/list/inkscape-devel%40lists.inkscape.org/2026/6/)
- **2.0:** no authoritative committed 2.0 feature roadmap or schedule was found. **Unknown.** Do not infer a 2.0 release plan from version speculation.
- **Animation:** Inkscape’s SVG overview says it does not provide animation and that no current GUI/underlying animation editor work is ongoing; older wiki pages contain proposals and GSoC concepts, not a shipped editor. [SVG overview](https://inkscape.org/en/develop/about-svg/) · [animation project concepts](https://wiki.inkscape.org/wiki/index.php/Projects)
- **Performance:** 1.3 introduced async multithreaded canvas rendering and reported 2–4× speed-up for zoom/pan/transform on multicore machines; this is a release-note claim for those operations, not a universal document benchmark. [1.3 notes](https://wiki.inkscape.org/wiki/Release_notes/1.3)

## Why it can be slow or large

Inkscape is not “Cairo plus SVG.” Its architecture stores both a generic XML representation tree and a typed object tree; the object tree maps XML into editable display primitives and is where much application behavior lives. Document changes propagate through notifications, object updates, undo, and redraw. [architecture overview](https://wiki.inkscape.org/wiki/Architectural_overview) · [SPDocument API](https://inkscape.gitlab.io/inkscape/doxygen/classSPDocument.html)

Likely workload bottlenecks (confidence: medium; these depend on document and version):

- **Huge object counts or high-node paths:** parsing, object creation, bounding-box updates, selection hit-testing, snapping, undo records, and display-list invalidation scale with content, not source-file MB alone.
- **Filters, masks, patterns, clones and nested transforms:** often expand intermediate raster work or dependency traversal; a tiny SVG can demand large intermediate surfaces.
- **Text:** font discovery, shaping, glyph bounds, and repeated text layout are expensive; 2026 developer notes identify glyph drawing/bounds as an optimization area. [June 2026 minutes](https://lists.inkscape.org/hyperkitty/list/inkscape-devel%40lists.inkscape.org/2026/6/)
- **CPU rendering:** Inkscape 1.3's OpenGL display mode accelerates panning/zooming/rotation, but release notes say the SVG content itself continues to render on CPU; it is not a full GPU renderer. [1.3 notes](https://wiki.inkscape.org/wiki/Release_notes/1.3)
- **Threading/invalidation:** parallel tiles help, but document mutation and complex patterns/effects may constrain safe parallel work. The canvas work describes tile parallelism, thread-safety constraints, and performance pathologies. [canvas MR](https://gitlab.com/inkscape/inkscape/-/merge_requests/4986) · [canvas performance MR](https://gitlab.com/inkscape/inkscape/-/merge_requests/3838)
- **Memory and bundle size:** exact baseline values are workload/build dependent and not published as comparable official metrics. GTK/Cairo/Pango/Poppler/libxml2/fonts/extensions and platform packaging all contribute; code written in C does not remove those costs.

**What C changes:** no automatic speed advantage over optimized C++ or Rust. C may reduce runtime/ABI complexity and make a compact core possible; it also makes ownership, bounds, lifetime, and error handling manual. Algorithm selection, cache invalidation, object virtualization, and renderer design dominate. C is a defensible product constraint, not a performance plan.
