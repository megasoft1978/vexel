# Goal
Remove the fixed 16 MiB source cap from the full-document decode path so that real large SVGs can be rendered, and replace it with an explicit, documented token-storage budget. This is the single highest-impact corpus blocker: 11 of the 39 render-tested corpus files fail at exactly offset `16777216`.

# Context pointers
- Read: `AGENTS.md`, `OWNER-DIRECTIVES.md`, `docs/adr/0016-product-target-and-gates.md`, `reports/M4/render-diagnostics.md`, `src/svg/shape/decode.c`, `src/svg/shape/traverse_internal.h`, `src/svg/xml/xml_tokenizer.h`, `src/svg/index/index.c` (the streaming-tokenizer pattern to follow), `src/svg/xml/xml_reader.c`.
- Root cause: `svg_shape_decode` rejects any source larger than `SHAPE_MAX_BYTES` (16 MiB) and otherwise allocates `source.len / 2 + 2` tokens. `svg_xml_token` is 96 bytes, so a 94 MiB document would need about 4.4 GiB of tokens. The index path already avoids this by using the streaming tokenizer (`svg_xml_token_stream_start` with a storage budget, `_step`, `_take`) and accepts up to 1 GiB.
- Frozen corpus evidence: `reports/M4/render-diagnostics.json`, manifest SHA-256 `9fbf9a2f384d70a41da72e99ac259d2c5d137ffd3c8a01ce4be4741c1c29bc30`.

# Existing contracts and invariants
- Source bytes are borrowed and immutable; the decoded document borrows them for its lifetime.
- Every existing limit (nesting depth, traversal visits, path commands, glyphs, `<use>` expansion, reference cycles, CSS, animation) stays exactly as it is. This order only replaces the *source-size* rejection and the *token allocation strategy*.
- `svg_shape_decode` must keep its signature and its `svg_shape_error` / `svg_shape_diagnostic` contract.
- Tokens transferred from the streaming tokenizer are allocated by the tokenizer; tokens allocated by the shape layer are tracked by its allocator. The two must not be freed through each other's paths.
- No new dependency, no network, C17, files under 800 lines.

# Required implementation
1. Replace `SHAPE_MAX_BYTES` with two explicit, documented constants in `src/svg/shape/traverse_internal.h`: an accepted source ceiling matching the reader/index ceiling (1 GiB), and a token-storage budget for the decode path (start at 256 MiB and state the resulting token count in the comment).
2. In `svg_shape_decode`, tokenize through the streaming API under that storage budget instead of `svg_xml_tokenize` with `source.len / 2 + 2` capacity. Follow the `validate_document` pattern in `src/svg/index/index.c`: `svg_xml_token_stream_start` → repeated `svg_xml_token_stream_step` → `svg_xml_token_stream_result` → `svg_xml_token_stream_take`.
3. Track token ownership explicitly: free stream-transferred tokens with `free()` and shape-allocated tokens with `svg_shape_free()`. The document destroy path and the decode error paths must both be correct and must not double-free or leak.
4. Map a stream failure caused by exhausted token storage to `SVG_SHAPE_ERROR_LIMIT` with the byte offset actually read, and map a stream grammar failure to the existing XML mapping. A document that exceeds the storage budget must fail cleanly, not abort or exhaust memory.
5. Add focused tests covering: (a) a well-formed document larger than 16 MiB decodes successfully and preserves its shapes; (b) a document whose token storage exceeds a deliberately tiny budget fails with `SVG_SHAPE_ERROR_LIMIT` and a usable offset without crashing; (c) the existing source-size ceiling is still enforced above 1 GiB; (d) token memory is released on both the success and failure paths (the project's allocation accounting must balance).
6. Re-run `scripts/corpus_render_report.py` and record the change in rendered-file count and in the failure histogram against the committed baseline.
